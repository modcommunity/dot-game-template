# Design

## The shape, and why each piece is the one it is

- **`TplGame` is the whole game, and the same class runs everywhere**: authoritative on a dedicated server and offline, a mirror on a connected client that only moves its own player. A second single-player copy of the rules would be a second game to keep in step.
- **`TplGame.step` is static and pure, because it is what prediction runs.** The server and the owning client call it with the same input for the same delta and agree. Nothing that differs between machines may reach it.
- **The module is a thin `DotGameModule`.** The netcode's four load-bearing settings, the seal, the roster, the tick and the reverse teardown are dot-game's; the template must not show a newcomer a second copy. The tick rate is `Engine.physics_ticks_per_second`, which the server set from `sv_tickrate`, because the module's tick IS the physics frame.
- **The bridge is the only file that names the game and dot-net.** Four things cross the wire, all through one `@rpc` node (`TplLink`) under the node named `Server` on each end: snapshots, inputs, events and requests.
- **A player is `SHARED` authority and `always_relevant`.** SHARED so the owner predicts and the server corrects (SERVER would leave a player a round trip behind their own keys). Always relevant because the arena is one screen; a bigger world wants interest management, and the comment says so.
- **The score is a replicated net var; the coins are events.** Deliberate teaching: state about an entity replicates and recovers from loss for free; a change to the world that is not an entity is an event.
- **READY before anything is sent.** The server seats a player on `client_spawn`, but for a game built into a client that happens before the client scene exists. The client sends READY once `is_playing()`; the server sends the hello, the coins and the roster on it, and handles READY arriving first. A delivered game builds its scene before spawn, but the template has to work both ways, and the suites run it both ways.
- **The client predicts with the DECODED input.** Eight bits per axis on the wire; predicting with the raw float would disagree with the server a little every tick. `client_tick` writes the command, reads it back, and simulates that.
- **Every input packet carries the last five commands** (`INPUT_COPIES`, `DotNetInput.write_batch`/`read_batch`). Inputs go unreliable, and with one command a packet every lost packet was a tick the server ran on the previous command and a correction on the client's screen. The copies come from dot-net's replay history, kept as decoded and not sanitised so a copy re-encodes to the same bits (`TplGame.step` bounds the length itself); the server skips copies of ticks it has already simulated, which would otherwise each count as a late input. `headless_net` drops a packet between a socketless bridge pair to prove it.
- **Your own player is drawn between its ticks, at the clock's render alpha.** A player this machine simulates moves once a tick, and a screen draws more often than that; drawn where the tick left it, it stood still on most frames and jumped on the rest. `TplGame.move` remembers where each tick began (`drawn_from`, `drawn_two_back`) and the view draws `Player.drawn_position(alpha)`. Connected, the alpha is dot-net's `DotNetClock.render_alpha()` rather than the engine's physics fraction: the clock stretches its ticks while it settles on the server, so a physics frame now and then runs no tick or two, and at the engine's fraction that frame stalls or moves double; `render_alpha` runs -1..2 for a moment and draws through it. Asked by name, so an older shell draws at the fraction. Offline every physics frame is one tick and the fraction is exact, so everybody is drawn this way. Somebody else's player on a client is never simulated there (`drawn_from` stays NAN) and is already smoothed by dot-net's interpolation. A step longer than a body's width is a teleport (a new arena, a correction) and is drawn where it landed. `headless_net` checks the connected view holds its netcode clock, then forces a no-tick and a two-tick frame on a clock nothing steers (over the socket the drift makes slips of its own at unchosen moments, and two in a row exceed the one tick `render_alpha` holds, which made the first version of the check fail one run in four) and checks neither stalls nor doubles, beside a control drawn at the fraction that does.
- **The client adopts the server's tick and snapshot rates from the hello**, and the engine's physics rate with them: interpolation draws at a fraction through a physics frame, which is a fraction through a tick only while the two rates match.
- **`net.service_scope = &"client"`**, so a server and a client in one process (every suite) do not replace each other's registry entry.
- **Keys are read with `Input.is_physical_key_pressed`, not actions.** `project.godot` does not travel in a pack, so an input map defined there does not exist in the shell that mounts the game.
- **The RPCs are `_rpc_*`, and that is not style.** The first version called one `_input`, which is Node's virtual: "The function signature doesn't match the parent", and every script preloading the link failed to compile.
- **Settings and the console are dot-menu's `DotMenuSettings` and dot-console's `DotConsoleKit`, set up by dot-game's `DotGameClient`**, the same as every game, with the loading cover, Tab, M and the input block, so a developer starts with the Escape menu, the Tab board and `net_stat` the players already know. Chat is dot-ui's `DotChatWindow` over dot-server's chat ([below](#chat-and-why-it-is-in)).

## Arenas and the M menu

M opens a map menu in every game in the family, solo and on a server, so it does here too. The template had one arena and no idea of a map; it now has three, as data.

- **An arena is a row in `tpl_arenas.gd`** (id, name, size, coin count, floor colour, a line for the menu), not a scene: Coin Grab's arena is a rectangle with coins in it, and a row of numbers is the smallest thing that is still a real map. A game with walls keeps a scene per map and lists them with dot-map's catalogue instead.
- **Every arena fits inside `TplGame.ARENA`**, which stayed the wire's range for positions and coins, so the netcode did not change. `TplGame.size` is the arena being played and `step` takes it as `walls`: it is the same on both ends (the server says which arena), so prediction stays pure. The view fits the largest arena to the window and centres the one being played, so Pocket looks small rather than zoomed.
- **One change path, `TplGame.change_arena`**: the new arena's size, a fresh layout of its coins and every score back to 0, and `arena_changed`. Solo the menu calls it; on a server the menu and a vote's winner both call it, and the bridge answers `arena_changed` with an ARENA event (the id) and the COINS, to every ready peer. A client takes the walls from ARENA with `use_arena`, which moves anybody outside them in, and never lays coins.
- **On a server the decision is the owner's.** dot-vote's `DotVoteMapMenu` answers `/mapmenu` (what dot-menu's `DotMenuMaps` sends on M) with the list and whether this player holds `sv_map_menu_flag` (`generic`, the flag every staff group from moderator up holds, by default; `changemap` for admins; `anyone` for everybody; the only player on a server changes it directly while `sv_map_menu_alone` is 1). A player without it gets the vote: choosing nominates the arena and rocks the vote. The menu is the server half of dot-vote's commands, so the module builds a director: no clock (`RTV_ONLY`), the winner played at once, twenty seconds to vote, "Don't change" on every ballot. Its lines go to the chat box as the server's own, with a numbered "Type !vote and a number" line, since chat is this game's only ballot. `!vote` is renamed from dot-vote's default `!votefor`.

## Chat, and why it is in

The template first shipped without chat, to keep the netcode the only new idea a developer meets. That was reversed on 2026-10-12: a game copied from it never showed the server's own lines (a vote announcing itself, "Ada joined", an admin's `say`, the reply to a `!` command) and had no `!sm`, and self-mute (`sm`) is to work in every game. The cost turned out to be one function in `tpl_client.gd`, because the game routes no chat itself:

- **dot-ui's `DotChatWindow` under the HUD root**, so the menu's theme and HUD size reach it. Y opens it (dot-ui registers the action at runtime, which is why it works in a pack where `project.godot`'s input map does not travel). No team key: the template has no teams.
- **Sent with `DotClientLink.send_chat`, drawn from `chat_received`.** dot-server's chat manager checks every line (rate, length, a gag), sends it to every playing session, the sender included, and runs a line starting with `!` or `/` as a console command with the speaker's permissions instead, which is how `!rtv`, `!vote` and the map menu's `/mapmenu` work. Drawing what comes back rather than what was typed means the box shows what the server accepted. `system` and `admin` lines are drawn by dot-game's `DotGameChatClient.draw_server_line`, the same as every game; `all`/`team` are drawn with the speaker in their disc's colour (a player id is the session's userid).
- **`sm` is dot-chat's `DotChatSelfMute`**, one list per process: the box runs `!sm`/`/sm` before `submitted` so it never reaches the server, the console's `sm` (from `DotConsoleKit`, present because dot-chat is linked) is the same list, and `_on_chat_line` drops a muted player's line by userid and name. `DotChatSelfMute.shared()` is called when the box is built, because the list is what asks the server for the roster.
- **Typing does not steer**: `_intent` returns zero while the box is open, before the steer hook, so a suite can prove it.
- **Offline, a line is echoed as "You"**: there is nobody to send it to, and a box that did nothing would read as broken.

A game that wants channels of its own (teams, proximity) or voice routes chat through dot-game's `DotGameServices` instead, with `send_chat`/`send_voice` on its bridge; mg-buses-from-hell's `bfh_services.gd` is the short example.

## The pack rules, enforced in three places

No `class_name`; every `res://` string naming the game's own files goes through `TplPaths.rebase()` where it is defined; `extends`/`preload` relative; `client_scene`, `scene` and `module` relative. The reasoning is dot-server-deploy's [delivery-constraint.md](../../dot-server-deploy/docs/delivery-constraint.md).

1. **`examples/headless_pack.tscn`**, here and in CI, scans every script for a `class_name` and every shipped script for a bare `"res://<a folder the game ships>/…"` outside a `…Paths.rebase("…")` call and outside comments. Both scanners run against a planted violation first, because a scanner gone blind reports a clean tree. It also asserts `rebase_onto` against a mount prefix (idempotent, `user://` untouched), the only way those properties can fail in a build, where `root()` is `res://`.
2. **`tools/check.sh` runs it** with the other suites and the rename test. It is a GDScript suite rather than a shell grep so that CI, which runs `examples/headless_*`, enforces it: a third-party developer's release is built by CI.
3. **dot-server-deploy's `examples/template_client.tscn`** packages this repository's git HEAD with dot-ci's `package.sh --pack --name dot-game-template` exactly as the release does, publishes the zip the way the site does (signed under `someone/dot-game-template`, a run key), stamps `game.yml` with the installer's `stamp_identity`, boots a real host, joins a real client and collects a coin. It is the only place this game runs mounted. **It packages HEAD: commit before believing it.**

## The rename

`tools/rename.sh <prefix> <repo>` rewrites `\btpl` → prefix, `\bTpl` → Prefix and `dot-game-template` → repo in every tracked or new file except Markdown, renames every `tpl_*` file, and deletes `.godot/`.

- **A prefix at all** because a game here has no `class_name`, so its file names are what keep it apart from every other game installed beside it.
- **Markdown is left alone** because the README and this repository's docs describe the template; renaming the guide's own clone URL would make it lie.
- **It refuses a repository name the site's `IsPackSegment` would refuse** (lowercase `a-z0-9-_`, no leading, trailing or doubled `_`), because that name becomes the second half of the pack's id.
- **`tools/check.sh` tests it every run**: copies the tree, links the addons, renames to `cr`/`crate-rush`, fails if any trace of the old names survives outside Markdown, then imports and runs all three suites on the copy. With the `Tpl` substitution dropped the renamed copy still PASSED every suite (the constants are local aliases); only the survivor check caught it.

## Running it locally against a server

A locally published pack is not enough for a local client: the client fetches content from the server's `content_urls` (the platform's origin by default) and mounts only packs signed by a key in `client/content.json`. So the README's step 5 serves `dist/` with `python3 -m http.server`, passes `--content-url`, and adds this machine's key to the shell's trust. It uses plain `./setup.sh` in dot-server-deploy, which links every addon; **`--only-games` derives the addon list from the named games and is the wrong flag for this** ([dot-server-deploy's setup.md](../../dot-server-deploy/docs/setup.md#--only-games-and---skip-games)).

## Map culling is opt in

A converted map carries its precomputed visibility, and dot-game's `DotGameClient` can draw only what the camera could see: call `platform.attach_visibility(world, drawn)` after the map is built (`world` the `DotMapBspMesh`, `drawn` its `build_node()` tree) and `platform.detach_visibility()` when it goes. Nothing changes until a player or the game picks a mode: `vis_mode` is `off` by default, and `pvs`, `occluders` or `both` at the client console (`vis_mode both`), on the command line (`--vis_mode=both`) or from code (`platform.set_vis_mode("both")`). Leave it off for small open maps, where culling costs more than it saves; turn it on for large indoor maps. dot-game's [client-migration.md](../../dot-game/docs/client-migration.md) has the details.
